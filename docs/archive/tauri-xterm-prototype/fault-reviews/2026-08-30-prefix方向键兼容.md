## 1. 问题描述

### 1.1 问题场景

在浏览器预览中先按 `Ctrl+B`，再由浏览器驱动发送向右方向键。Prefix 提示正确进入并退出，但活动窗格没有从左侧主窗格移动到右上窗格。

### 1.2 具体表现

- 操作前活动 Pane 为 `preview-pane-main`，revision 为 `r1`。
- 第二键被 Prefix 状态机消费，但操作后活动 Pane 和 revision 均未变化。
- 用鼠标点击 `preview-pane-build` 可以正常切换并把 revision 更新为 `r2`，因此布局算法和命令队列不是根因。

### 1.3 错误信息

没有异常或控制台错误；这是一个静默的键名匹配失败。运行时观测为：

```text
Ctrl+B -> Prefix active
direction key -> Prefix inactive
activePaneId = preview-pane-main
revision = r1
```

## 2. 临时解决方案

没有采用临时绕过；定位后直接修正键名规范化逻辑。

## 3. 根本原因分析

### 3.1 问题分析过程

1. Prefix 提示能出现，证明 `Ctrl+B` 捕获和超时状态正常。
2. 第二键后 Prefix 提示消失，证明全局 capture 监听器收到了按键。
3. 点击右上 Pane 能正确更新活动 Pane，排除了几何导航、preview service 和 React snapshot 替换问题。
4. 单元测试只覆盖标准 DOM 键名 `ArrowLeft/ArrowUp/ArrowDown`，没有覆盖驱动或旧环境可能产生的 `Left/Right/Up/Down`。
5. 最终定位到 `DIRECTIONS` 对原始 `event.key` 做精确匹配，未先规范化键名。

### 3.2 直接原因

相关代码位置：`src/keyboard/prefix.ts`。

修改前：

```ts
const DIRECTIONS = {
  ArrowLeft: "left",
  ArrowRight: "right",
  ArrowUp: "up",
  ArrowDown: "down",
};

const direction = DIRECTIONS[key.key];
```

当输入为 `Right` 时查表失败，命令被解析成 `unknown`。

### 3.3 根本原因

- 设计层面：Prefix 解析器把浏览器原始键名直接当成领域方向，没有设置输入规范化边界。
- 开发层面：实现只考虑现代浏览器标准键名，没有考虑旧键名和自动化驱动差异。
- 流程层面：初始测试覆盖了修饰键组合，却没有建立方向键别名矩阵。

### 3.4 为什么没有提前发现

- 单元测试直接构造 `Arrow*`，与实现使用了相同假设。
- 静态构建和 TypeScript 类型检查无法发现合法字符串值之间的语义差异。
- 只有实际 Prefix 两段按键链路验证能暴露这个静默 no-op。

## 4. 解决方案

### 4.1 根本解决方案

修改文件：`src/keyboard/prefix.ts`、`src/keyboard/prefix.test.ts`。

修改后：

```ts
const DIRECTIONS = {
  left: "left",
  right: "right",
  up: "up",
  down: "down",
};

const direction = DIRECTIONS[key.key.toLocaleLowerCase().replace(/^arrow/, "")];
```

解析器先转小写，再去掉可选的 `arrow` 前缀，因此标准键名、旧键名和大小写差异会落到同一个领域方向。新增 `Right -> right` 单元测试。

### 4.2 影响范围评估

变更只扩展方向键输入集合，不改变 `Arrow*` 的既有行为，也不影响普通字符、修饰键优先级或 Prefix 超时。修复后浏览器运行验证中活动 Pane 更新为 `preview-pane-build`，revision 从 `r1` 更新为 `r2`。

## 6. 经验总结（一句话）

> 键盘事件应在输入边界先规范化为领域命令，不能让浏览器或自动化驱动的键名差异进入业务逻辑。
